# GitHub distribution facts for the transcription app

Checked 2026-09-02. Every fact is followed by the URL it was read from. Where something could not be verified on a primary source it is labelled "not verified".

## Summary (the facts that change decisions)

1. ghcr.io container images are currently free for storage and bandwidth even while private (GitHub promises one month's notice before that changes); no single layer may exceed 10 GB; a package's visibility does not follow the repository, and making it public is irreversible.
2. Private repositories on the Free organisation plan get 2,000 hosted-runner minutes a month; public repositories and self-hosted runners cost nothing; standard runners guarantee only 14 GB of free disk (about 10 to 30 GB is recoverable by deleting preinstalled tools); larger runners need the Team plan and are always billed.
3. On the Free plan, secret scanning alerts, repository push protection and private vulnerability reporting exist only for public repositories; Dependabot and SECURITY.md work everywhere.
4. Neither classic branch protection nor rulesets can be applied to a private repository on the Free plan; both switch on the day the repository goes public.
5. Flipping private to public publishes the whole history; forks and cached views keep anything ever committed, so scan the history for secrets before the flip.
6. Licence: 17 U.S.C. 105 (no US copyright in government work) plus a CC0 1.0 dedication for the rest of the world is the 18F/GSA pattern; CC0 is not OSI-approved, but GitHub's licence detection handles it.
7. Every pinned library is permissive (MIT, BSD, Apache-2.0, PostgreSQL), including the Whisper and Qwen3 weights; the pyannote community-1 weights are CC-BY-4.0 behind a Hugging Face gate that every installing office must click through.
8. nvidia/cuda base images are under NVIDIA's proprietary container licence, which allows distributing a derived image that adds material functionality but not the image as a stand-alone product.
9. Ubuntu 24.04's ffmpeg is built GPL-2+ (it links libx264); calling it as a subprocess leaves the app's licence alone, but shipping it inside an image obliges the publisher to make its source available.
10. Compose with both image: and build: pulls first and builds only if the image is not found; digest pinning works; gitleaks-action needs a licence key for organisations (free for one repository), while the MIT gitleaks CLI and AGPL trufflehog need none.

## 1. GitHub Packages and the Container Registry (ghcr.io)

- Public packages are free: "GitHub Packages usage is free for public packages. In addition, data transferred in from any source is free." https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-packages/about-billing-for-github-packages
- Container images are currently free even when private. The billing page says, under "Billing for container image storage": "Container image storage and bandwidth for the Container registry is currently free. If you use Container registry, you'll be informed at least one month in advance of any change to this policy." Same URL. Treat this as a policy that can change with one month's notice, not a permanent entitlement.
- Included quota for private packages in the other registries (the fallback if the container exemption ends), same page: GitHub Free and Free for organizations 500 MB storage and 1 GB/month transfer; Team 2 GB and 10 GB/month; Enterprise Cloud 50 GB and 100 GB/month. Downloads by a workflow using GITHUB_TOKEN do not count. Overage prices are not printed there.
- Size limits: "The Container registry has a 10 GB size limit for each layer" and "a 10 minute timeout limit for uploads". There is no documented whole-image limit. A 12 GB CUDA image is fine as long as no single layer exceeds 10 GB, so keep the PyTorch/CUDA install and the WhisperX install in separate layers. https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry
- Visibility does not follow the repository. "When you first publish a package, the default visibility is private and only you can see the package." A package linked to a repository (for example via the org.opencontainers.image.source label, set before the first push) "automatically inherits the access permissions (but not the visibility) of the linked repository". https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility
- Making a package public: package page > Package settings > Danger Zone > Change visibility > Public > type the package name > confirm. "Once you make a package public, you cannot make it private again." Same URL.
- Retention: no expiry is documented. Deleted packages or versions can be restored within 30 days, and "You cannot delete a public package if any version of the package has more than 5,000 downloads" without GitHub Support. https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package

## 2. GitHub Actions

- Included hosted-runner minutes for private repositories: GitHub Free 2,000 minutes/month (500 MB artifact storage); GitHub Free for organizations 2,000 minutes/month; GitHub Pro 3,000; GitHub Team 3,000 (2 GB storage); GitHub Enterprise Cloud 50,000. https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions and https://docs.github.com/en/get-started/learning-about-github/githubs-plans
- Public repositories and self-hosted runners: "GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners." (billing page above). The plans page repeats it: "GitHub Actions usage is free for standard GitHub-hosted runners in public repositories, and for self-hosted runners." So a self-hosted runner on the office's own server costs no minutes, private or public.
- Standard runner hardware, Linux: public repositories get 4 vCPU, 16 GB RAM, "14 GB" SSD; private repositories get 2 vCPU, 8 GB RAM, 14 GB SSD. https://docs.github.com/en/actions/reference/runners/github-hosted-runners
- The 14 GB figure is a floor, not the physical disk. A GitHub runner-images maintainer wrote "we provide at least 14 GB of free space" and gave the standard workaround: sudo rm -rf /usr/share/dotnet, /opt/ghc, /usr/local/share/boost and "$AGENT_TOOLSDIRECTORY". https://github.com/actions/runner-images/issues/2840#issuecomment-790492173
- The jlumbroso/free-disk-space action (MIT, Linux only) automates that and reports roughly 31 GB reclaimable (Android 14 GB, tool cache 5.9 GB, misc packages 5.3 GB, swap 4 GB, .NET 2.7 GB). https://github.com/jlumbroso/free-disk-space
- Larger runners (paid): "Larger runners are available for organizations and enterprises on GitHub Team and GitHub Enterprise Cloud plans" (runners reference above). Linux sizes run from 2 vCPU/8 GB/75 GB SSD (4 vCPU has 150 GB, 8 vCPU 300 GB) up to 96 vCPU/384 GB/2040 GB. https://docs.github.com/en/actions/reference/runners/larger-runners They "are not eligible for the use of included minutes on private repositories" and are "always billed at the per-minute rate" (Linux 2-core x64 $0.006/min). https://docs.github.com/en/actions/using-github-hosted-runners/using-larger-runners/about-larger-runners

## 3. Security features by plan and visibility

- Secret scanning alerts: "Public repositories: Secret scanning runs automatically for free." "Organization-owned private and internal repositories: Available with GitHub Secret Protection enabled on GitHub Team or GitHub Enterprise Cloud." https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning
- Secret Protection cannot be bought on the Free plan: "You must be on a GitHub Team or GitHub Enterprise plan in order to purchase GitHub Code Security or GitHub Secret Protection." https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security Price: "$19 USD per active committer/month" for Secret Protection, "$30 USD per active committer/month" for Code Security. https://github.com/security/advanced-security
- Push protection: repository-level push protection "Requires GitHub Secret Protection to be enabled" (not available on a private Free-plan repo). The separate "push protection for users" feature "Is enabled by default" and "Stops you from pushing secrets to public repositories on GitHub". https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection and https://docs.github.com/en/code-security/getting-started/github-security-features
- Free on every plan and visibility ("Available for all GitHub plans"): security policy (SECURITY.md), Dependabot alerts and security updates, Dependabot version updates, dependency graph. https://docs.github.com/en/code-security/getting-started/github-security-features
- Private vulnerability reporting: "Owners and administrators of public repositories can allow security researchers to report vulnerabilities securely in the repository by enabling private vulnerability reporting." Enabled under Settings > Advanced Security > Private vulnerability reporting. Public repositories only. https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository
- Branch protection (classic): "Protected branches are available in public repositories with GitHub Free and GitHub Free for organizations. Protected branches are also available in public and private repositories with GitHub Pro, GitHub Team, GitHub Enterprise Cloud, and GitHub Enterprise Server." Each rule by default "disables force pushes to the matching branches and prevents the matching branches from being deleted". https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- Rulesets have the same restriction: "Rulesets are available in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise Cloud." Rulesets and classic rules "work alongside each other, and all applicable rules are enforced"; up to 75 rulesets per repository. https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets
- Net effect on Free: a private repository can have neither classic branch protection nor rulesets; both become available when it goes public or the org moves to Team.

## 4. Flipping private to public

- GitHub's own warning list when making a repository public: "The code will be visible to everyone who can visit GitHub.com." "Anyone can fork your repository." "Actions history and logs will be visible to everyone." "Stars and watchers for this repository will be erased." "The repository will automatically gain access to GitHub Advanced Security features." The whole git history goes with the code; there is no tip-only option. https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility
- Secrets in history: "if the sensitive data you need to remove is a secret (e.g. password/token/credential), as is often the case, then as a first step you need to revoke and/or rotate that secret." https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
- Rewriting is not enough on its own. After a rewrite and force push, commits with the data "may still be accessible elsewhere: In any clones or forks of your repository; Directly via their SHA-1 hashes in cached views on GitHub; Through any pull requests that reference them." Cached views and PR references are removed only "by contacting us through the GitHub Support portal", and "If the commit that introduced the sensitive data exists in any forks, it will continue to be accessible there." GitHub recommends git-filter-repo 2.47 or later with --sensitive-data-removal. Same URL. Scan the full history (section 9) before the flip.

## 5. Licence facts

- 17 U.S.C. 105(a): "Copyright protection under this title is not available for any work of the United States Government, but the United States Government is not precluded from receiving and holding copyrights transferred to it by assignment, bequest, or otherwise." https://www.law.cornell.edu/uscode/text/17/105
- 17 U.S.C. 101 defines such a work as "a work prepared by an officer or employee of the United States Government as part of that person's official duties." https://www.law.cornell.edu/uscode/text/17/101 The statute is silent on copyright outside the US, which is why federal projects add CC0.
- The federal notice pattern, verbatim from 18F: "As a work of the United States government, this project is in the public domain within the United States of America. Additionally, we waive copyright and related rights in the work worldwide through the CC0 1.0 Universal public domain dedication." https://raw.githubusercontent.com/18F/open-source-policy/master/LICENSE.md GSA's policy repository carries the same text. https://raw.githubusercontent.com/GSA/open-source-policy/master/LICENSE.md
- OMB M-16-21 (2016) says only that agencies "shall append appropriate OSS licenses to the source code" (section 7.5); it never mentions public domain. https://obamawhitehouse.archives.gov/sites/default/files/omb/memoranda/2016/m_16_21.pdf The code.gov licensing page now redirects to digital.gov without licensing text; not verified.
- CC0 is not OSI-approved. OSI FAQ: "At this time, we do not recommend releasing software using the the CC0 public domain dedication." CC0 was submitted in February 2012; "the License Review Committee was unable to reach consensus that it should be approved, and Creative Commons eventually withdrew the application", the sticking point being clause 4(a). https://opensource.org/faq That clause reads: "No trademark or patent rights held by Affirmer are waived, abandoned, surrendered, licensed or otherwise affected by this document." https://creativecommons.org/publicdomain/zero/1.0/legalcode The same FAQ calls US government public-domain software "effectively open source, or open source for most practical purposes".
- It does not matter for GitHub. choosealicense.com lists CC0-1.0 (permissions: commercial use, distribution, modification, private use; no conditions; limitations: liability, patent use, trademark use, warranty). https://choosealicense.com/licenses/cc0-1.0/ GitHub detects licences with "the open source Ruby gem Licensee" against that list; "The license picker is only available when you create a new project", so an existing repository only needs a LICENSE file. A LICENSE file with extra text may not be detected: "simplify your LICENSE file and note the complexity somewhere else, such as your repository's README file." https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository
- Comparison from choosealicense.com: MIT is "A short and simple permissive license with conditions only requiring preservation of copyright and license notices"; no patent grant. https://choosealicense.com/licenses/mit/ Apache-2.0 is permissive and "Contributors provide an express grant of patent rights"; conditions are licence and copyright notice and state changes; limitation: trademark use. https://choosealicense.com/licenses/apache-2.0/ AGPL-3.0 is the "strongest copyleft license"; conditions are disclose source, same license, state changes and "Network use is distribution", defined as "Users who interact with the licensed material via network are given the right to receive a copy of the source code"; it also grants patent rights. https://choosealicense.com/licenses/agpl-3.0/ and https://choosealicense.com/appendix/

### ffmpeg

- Default licence: "FFmpeg is licensed under the GNU Lesser General Public License (LGPL) version 2.1 or later. However, FFmpeg incorporates several optional parts and optimizations that are covered by the GNU General Public License (GPL) version 2 or later. If those parts get used the GPL applies to all of FFmpeg." The LGPL checklist says "Compile FFmpeg without '--enable-gpl' and without '--enable-nonfree'" and "Make sure your program is not using any GPL libraries (notably libx264)." https://ffmpeg.org/legal.html
- Upstream LICENSE.md lists the GPL external libraries (libx264, libx265, libxvid and others) and says --enable-nonfree (FDK-AAC, OpenSSL) makes "the resulting binary ... unredistributable". https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/LICENSE.md
- Ubuntu 24.04 (noble) ships ffmpeg 7:6.1.1-3ubuntu5 in universe. https://packages.ubuntu.com/noble/ffmpeg Its libavcodec60 depends on libx264-164, libx265-199 and libxvidcore4. https://packages.ubuntu.com/noble/libavcodec60 The package copyright file states: "For building the default Debian packages some of the GPL licensed files are used, so the resulting binaries are licensed under GPL v2+. For libavcodec/libavfilter an extra flavor is built, which links against external libraries licensed under the Apache License 2.0, which makes it effectively licensed under the GPL v3+." https://changelogs.ubuntu.com/changelogs/pool/universe/f/ffmpeg/ffmpeg_6.1.1-3ubuntu5/copyright Debian's current copyright file uses the same wording. https://metadata.ftp-master.debian.org/changelogs/main/f/ffmpeg/ffmpeg_7.1.5-0+deb13u1_copyright
- What this means for the app. First, running the ffmpeg binary as a subprocess does not make the app GPL: "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs" https://www.gnu.org/licenses/gpl-faq.html#MereAggregation and "A main program that uses simple fork and exec to invoke plug-ins and does not establish intimate communication between them results in the plug-ins being a separate program" https://www.gnu.org/licenses/gpl-faq.html#GPLPlugins , in which case "the license of the plug-in makes no requirements about the main program". https://www.gnu.org/licenses/gpl-faq.html#NFUseGPLPlugins
- Second, publishing a Docker image that contains Ubuntu's ffmpeg is distributing GPL binaries, and "if you distribute binaries, you must distribute the complete corresponding source code too." https://www.gnu.org/licenses/gpl-faq.html#UnchangedJustBinary GPLv3 section 6(d) allows pointing at source on another server provided "the source remains available for as long as you distribute the object code" https://www.gnu.org/licenses/gpl-faq.html#SourceAndBinaryOnDifferentSites ; under GPLv2 a physical-media offer may still be required. https://www.gnu.org/licenses/gpl-faq.html#DistributeWithSourceOnInternet Practical options: record the exact ffmpeg and codec package versions in each release and keep their source packages retrievable (Launchpad keeps them), or build ffmpeg without --enable-gpl, which the app can afford because it only needs decoding and resampling to 16 kHz WAV, not an H.264 encoder.

## 7. Distribution conventions

- Keep a Changelog 1.1.0: "Changelogs are for humans, not machines"; one entry per version, grouped by type, linkable, newest first, dated, and "Mention whether you follow Semantic Versioning". Change types: Added, Changed, Deprecated, Removed, Fixed, Security. "Keep an Unreleased section at the top to track upcoming changes." https://keepachangelog.com/en/1.1.0/
- Semantic Versioning 2.0.0: increment "MAJOR version when you make incompatible API changes, MINOR version when you add functionality in a backward compatible manner, PATCH version when you make backward compatible bug fixes"; pre-releases append a hyphen (1.0.0-alpha, 1.0.0-rc.1); "Major version zero (0.y.z) is for initial development"; and "No, 'v1.2.3' is not a semantic version. However, prefixing a semantic version with a 'v' is a common way (in English) to indicate it is a version number", so tag v1.2.3 for version 1.2.3. https://semver.org/spec/v2.0.0.html
- GitHub Releases: "Releases are based on Git tags, which mark a specific point in your repository's history." Assets: "Up to 1000 release assets may be associated with a single release. Each file included in a release must be under 2 GiB. There is no limit on the total size of a release, nor bandwidth usage." https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases
- Subscribing to releases only: on the repository page, "select the 'Watch' drop-down menu, then click a watch option. If you want to further customize notifications, click Custom, then select specific events", where the event types are "issues, pull requests, releases, security alerts, or discussions". So Watch > Custom > Releases. https://docs.github.com/en/account-and-profile/managing-subscriptions-and-notifications-on-github/setting-up-notifications/configuring-notifications
- Community health files: CODE_OF_CONDUCT.md, CONTRIBUTING.md, FUNDING.yml, issue and PR templates, SECURITY.md, SUPPORT.md. Precedence when a file could live in several places: "The .github folder, The root of the repository, The docs folder." Organisation-wide defaults go in a repository named .github, which "must be public". https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file
- CONTRIBUTING.md in root, docs or .github is linked from new issues and pull requests and shown as a "Contributing" tab. https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors
- SECURITY.md is created from the repository's Security tab ("Security policy" > "Start setup") and should list supported versions and how to report a vulnerability. https://docs.github.com/en/code-security/getting-started/adding-a-security-policy-to-your-repository
- CODEOWNERS lives in ".github/, root, or docs/", must be under 3 MB, and only requests reviews; enforcing them needs "Require review from Code Owners" in a branch protection rule or a ruleset, which (section 3) a private Free-plan repository cannot have. https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners
- Insights > Community Standards shows which of these files (plus README, licence and templates) are present. https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/accessing-a-projects-community-profile

## 8. Docker Compose

- pull_policy values: always ("Compose always pulls the image from the registry"), never ("relies on the platform cached image. If there is no cached image, a failure is reported"), missing ("Compose pulls the image only if it's not available in the platform cache. This is the default option if you are not also using the Compose Build Specification"), build ("Compose builds the image. Compose rebuilds the image if it's already present"), plus daily, weekly and every_<duration>. https://docs.docker.com/reference/compose-file/services/
- Both image: and build: present: "When Compose is confronted with both a build subsection for a service and an image attribute, it follows the rules defined by the pull_policy attribute. If pull_policy is missing from the service definition, Compose attempts to pull the image first and then builds from source if the image isn't found in the registry or platform cache." The built image is tagged with the image: name, which is also what docker compose push uses. https://docs.docker.com/reference/compose-file/build/
- So an office that clones a tag and runs docker compose up pulls the published ghcr.io image and builds locally only if the pull fails; developers force a build with pull_policy: build in an override file or --build.
- Digest pinning is supported: image "must follow the Open Container Specification addressable image format, as [<registry>/][<project>/]<image>[:<tag>|@<digest>]", with the example image: redis@sha256:0ed5d5928d4737458944eb604cc8509e245c3e19d02ad83935398bc4b991aac7. Same services URL. Note the docs' caveat that "The latest tag is always pulled even when the missing pull policy is used."
- CLI: docker compose up --pull always|missing|never, --build ("Build images before starting containers"), --no-build. https://docs.docker.com/reference/cli/docker/compose/up/

## 9. gitleaks and alternatives

- The gitleaks CLI is MIT. https://raw.githubusercontent.com/gitleaks/gitleaks/master/LICENSE Its README never mentions a licence key; current commands are gitleaks git -v, gitleaks dir, and stdin mode, and it documents a pre-commit hook (repo gitleaks/gitleaks, hook id gitleaks). https://github.com/gitleaks/gitleaks
- gitleaks-action changed licence at v2.0.0: "Since v2.0.0 of Gitleaks-Action, the license has changed from MIT to a license. Prior versions to v2.0.0 of Gitleaks-Actions will remain under the MIT license." The README: "If you are scanning repos that belong to an organization account, you will need to obtain a free license key"; personal accounts need none; the key comes from a Google form asking for name, email and company and is stored as the GITLEAKS_LICENSE secret. https://raw.githubusercontent.com/gitleaks/gitleaks-action/master/README.md
- The governing text is a "GITLEAKS-ACTION END-USER LICENSE AGREEMENT" with Gitleaks LLC: "There are various license tiers available for purchase. Each tier specifies a limit on the number of code repositories". https://raw.githubusercontent.com/gitleaks/gitleaks-action/master/LICENSE.txt The v2 notes: "A 'Starter' license to scan 1 repo is free, but scanning more than 1 repo belonging to the same organization requires a paid license." https://raw.githubusercontent.com/gitleaks/gitleaks-action/master/v2.md Paid tier prices are not published on gitleaks.io; not verified. https://gitleaks.io/
- Free alternatives: run the MIT CLI binary directly in a workflow step (no key, no EULA), or TruffleHog, which "Since v3.0 ... is released under a AGPL 3 license" and provides an action used as trufflesecurity/trufflehog@main with no key or payment mentioned anywhere in its README (its paid product is a separate enterprise offering). https://github.com/trufflesecurity/trufflehog and https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/LICENSE AGPL on a scanner you only run, not ship, imposes nothing on the app.
