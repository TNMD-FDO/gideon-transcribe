# App queue and worker facts: Postgres-backed task queues, scheduling, live status

Research date: 2026-09-02, gathered for the "background worker and scheduler" decision in Gideon Transcribe (Django 5.x/6.x, Postgres already in the Compose stack, 100% local, free and open-source only, as few containers as possible). Primary sources only: PyPI, the projects' own docs, their GitHub repositories, and the Django, PostgreSQL, Caddy, htmx and gunicorn docs. Every bullet ends with its source and the date it was checked. "Unverified" marks anything that could not be confirmed from a primary source.

## Summary for the decision

1. Postgres only, covers every need in the ticket (CPU queue with a concurrency cap, the 3-second poller, LLM calls, cron jobs): Procrastinate 3.9.0 (MIT, 2026-06-20, nine releases and 100+ commits in 12 months). LISTEN/NOTIFY plus polling, `@app.periodic(cron=...)` with a once-per-period guarantee across workers, retries, `--concurrency`, named queues, locks and queueing locks, heartbeat-based crash recovery, Django admin with retry/cancel/abort. The worker needs psycopg 3 installed.
2. Postgres only, second real option: Huey 3.3.4 (MIT, 2026-08-05) with its new `PostgresHuey` backend (psycopg 3.2+, `SKIP LOCKED` dequeue), cron `periodic_task`, retries, thread/process workers, Django admin dashboard, and a Django 6 Tasks backend. Caveats: only one consumer may enqueue periodic tasks (`-n` on the rest), no documented recovery of jobs lost to a crashed worker, and a single maintainer.
3. Postgres only but thin: Django 6.x `django.tasks` plus django-tasks-db 0.13.0 (BSD-3, 2026-08-28, PyPI status "Beta"): a `db_worker` command and `run_after` delays, but no retries, no cron, one task at a time per worker process, and no crash recovery found.
4. Postgres only, do-it-yourself: a `select_for_update(skip_locked=True)` poller (Django 1.11+, PostgreSQL 9.5+). The primitive is solid; retries, cron, crash recovery and an admin page would all be written and maintained in-house.
5. Need Redis or Valkey: RQ 2.12 with django-rq 4.2 (Redis >= 5 or Valkey >= 7.2; cron needs a separate `rq cron` process; rq-scheduler has had no release since 2024-10) and Celery 5.6.3 (only Redis and RabbitMQ are stable brokers; the SQLAlchemy broker is experimental; `beat` is a separate single-instance process). Two to three extra containers.
6. Built-in cron scheduling: Procrastinate, Huey, Celery beat, RQ (`rq cron`). Not built in: django.tasks / django-tasks-db (only `run_after`) and the hand-rolled poller.
7. Licence flags: Redis 7.4 to 7.8 are RSALv2/SSPLv1 only (Redis itself says "no longer open source under the OSI definition"); Redis 8 adds OSI-approved AGPLv3, so Redis 8 (under AGPL) and Valkey 9.1.2 (BSD-3-Clause, Linux Foundation) both pass a free-and-open-source-only rule, Valkey with the simpler permissive licence. Every Python package here is MIT, BSD-2 or BSD-3; Django BSD-3; Caddy Apache-2.0; htmx 0BSD.
8. Live status by SSE: `StreamingHttpResponse` needs an ASGI server (uvicorn, or gunicorn's new ASGI/uvicorn worker); gunicorn sync workers hold one worker per open connection. Caddy already flushes `text/event-stream` responses; `flush_interval -1` is the explicit form. django-eventstream 5.3.4 (MIT) runs on plain ASGI with no Channels.
9. Live status by polling: HTMX `hx-trigger="every 5s"` (2.0.10 on npm `latest`, 0BSD) needs no special server, proxy line or extra package, and is the lowest-risk default for a small office app; SSE can be added later without changing the queue.
10. Shape the facts support: Django web container, one or two Procrastinate worker containers (`media` queue at `--concurrency=4`; `default` queue for poller, LLM and cron), the existing Postgres, Caddy in front; no Redis, no beat, no scheduler container.

## 1. Procrastinate (Postgres-based task queue for Python)

- Latest release: 3.9.0, uploaded to PyPI 2026-06-20 (GitHub release published the same day). Earlier 12 months: 3.5.3 (2025-09-26), 3.6.0 (2025-12-08), 3.7.0 to 3.7.3 (2026-01-17 to 2026-03-28), 3.8.0 and 3.8.1 (2026-04-06 and 2026-04-08), 3.9.0; nine releases between 2025-09-02 and 2026-09-02. (source: https://pypi.org/pypi/procrastinate/json and https://github.com/procrastinate-org/procrastinate/releases, checked 2026-09-02)
- Licence: MIT ("MIT License", copyright PeopleDoc 2019-2021, then Joachim Jablon, Eric Lemoine, Kai Schlamp). PyPI classifier "License :: OSI Approved :: MIT License"; GitHub reports SPDX "MIT". (source: https://github.com/procrastinate-org/procrastinate/blob/main/LICENSE.md and https://pypi.org/pypi/procrastinate/json, checked 2026-09-02)
- Python: `requires_python >=3.10`; 3.7.0 (2026-01-17) dropped Python 3.9 and added 3.14. CI matrix tests Python 3.10 through 3.14 against PostgreSQL 14 through 18. README states "Python 3.10+" and "PostgreSQL 13+". (source: https://pypi.org/pypi/procrastinate/json, https://procrastinate.readthedocs.io/en/stable/changelog.html, https://github.com/procrastinate-org/procrastinate/blob/main/.github/workflows/ci.yml, https://github.com/procrastinate-org/procrastinate, checked 2026-09-02)
- Django: the `django` extra declares `django>=2.2`; the docs say Procrastinate "is tested with the latest Django version supported for each Python version it supports". An explicit list of tested Django versions was not found (unverified beyond that statement). (source: https://github.com/procrastinate-org/procrastinate/blob/main/pyproject.toml and https://procrastinate.readthedocs.io/en/stable/howto/django/configuration.html, checked 2026-09-02)
- Development status classifier: "5 - Production/Stable". (source: https://pypi.org/pypi/procrastinate/json, checked 2026-09-02)
- Django integration, install and setup: `pip install 'procrastinate[django]'`, add `"procrastinate.contrib.django"` to `INSTALLED_APPS`, then `./manage.py migrate`. A ready-made app object lives at `procrastinate.contrib.django.app`; task modules are auto-discovered from each app's `tasks.py` (setting `PROCRASTINATE_AUTODISCOVER_MODULE_NAME`, default "tasks"). (source: https://procrastinate.readthedocs.io/en/stable/howto/django/configuration.html, https://procrastinate.readthedocs.io/en/stable/howto/django/basic_usage.html, https://procrastinate.readthedocs.io/en/stable/howto/django/settings.html, checked 2026-09-02)
- Migrations: shipped as ordinary Django migrations, applied with `./manage.py migrate`, "always kept in sync with your current version of Procrastinate". Since 3.0.0 migrations are split into `pre` (run before deploying new code) and `post` (run after) for zero-downtime upgrades; for a small single-host app both simply run with `migrate`. (source: https://procrastinate.readthedocs.io/en/stable/howto/django/migrations.html and https://procrastinate.readthedocs.io/en/stable/changelog.html, checked 2026-09-02)
- Models: `ProcrastinateJob`, `ProcrastinateEvent`, `ProcrastinatePeriodicDefer`, `ProcrastinateWorker`; "read-only by default. You can't create, update or delete jobs or events through the ORM." (source: https://procrastinate.readthedocs.io/en/stable/howto/django/models.html, checked 2026-09-02)
- Management command and worker start: `./manage.py procrastinate worker` (same sub-commands as the standalone CLI except `schema`, which Django migrations replace); `./manage.py procrastinate healthchecks` checks connection, migrations and app. Defer from a view with `mytask.defer(...)` or `await mytask.defer_async(...)`. (source: https://procrastinate.readthedocs.io/en/stable/howto/django/basic_usage.html, checked 2026-09-02)
- Worker options: `worker` "Launch a worker, listening on the given queues (or all queues)"; arguments include `queues`, `name`, `concurrency`, `wait`, `fetch_job_polling_interval`, `listen_notify`, `install_signal_handlers`; every CLI flag has a `PROCRASTINATE_*` environment-variable equivalent. On SIGINT/SIGTERM the worker finishes running jobs before exiting (graceful shutdown; 3.0.0 added `shutdown_graceful_timeout`). (source: https://procrastinate.readthedocs.io/en/stable/howto/basics/command_line.html, https://procrastinate.readthedocs.io/en/stable/howto/basics/worker.html, https://procrastinate.readthedocs.io/en/stable/changelog.html, checked 2026-09-02)
- Periodic tasks (cron): `@app.periodic(cron="0 * * * *")` stacked on `@app.task`; "The cron syntax is on 5 columns (minute, hour, day, month, day of week). Here, an optional 6th column is supported for seconds." The task receives a `timestamp` argument. "Internally, each worker is responsible for ensuring that each periodic task is deferred in time, and the database is responsible for making sure deferring only happens once per period, even with multiple workers." Several schedules for one task via `periodic_id`. Uses the `croniter` dependency. (source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/cron.html and https://pypi.org/pypi/procrastinate/json, checked 2026-09-02)
- One-off delays: `task.configure(schedule_at=<datetime>)` or `schedule_in={"hours": 1, "minutes": 30}`; "it will run at the first opportunity after that date". (source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/schedule.html, checked 2026-09-02)
- Retries: `@app.task(retry=5)` (five retries), `retry=True` (until success), or `RetryStrategy(max_attempts=, wait=, linear_wait=, exponential_wait=, retry_exceptions={...})`; custom strategies subclass `BaseRetryStrategy` and can change queue, lock and priority per attempt. 3.4.0 (2025-07-18) added manual "Retry Failed Job". (source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/retry.html and https://github.com/procrastinate-org/procrastinate/releases/tag/3.4.0, checked 2026-09-02)
- Per-worker concurrency: `app.run_worker(concurrency=30)` or `procrastinate worker --concurrency=30`; concurrency is asyncio-based ("while a job is waiting for external I/O ... the CPU is free to run other jobs"). Synchronous task functions are run through `asgiref.sync.sync_to_async`, that is, in threads. For CPU-bound ffmpeg jobs the natural fit is a worker on a `media` queue with `--concurrency=4`, where each job just waits on a subprocess. (source: https://procrastinate.readthedocs.io/en/stable/howto/production/concurrency.html and https://procrastinate.readthedocs.io/en/stable/discussions.html, checked 2026-09-02)
- Named queues: tasks take `queue=`; a worker started without queue names listens "to every queue"; `procrastinate worker [queue ...]` restricts it. (source: https://procrastinate.readthedocs.io/en/stable/howto/basics/worker.html and https://procrastinate.readthedocs.io/en/stable/howto/advanced/cron.html, checked 2026-09-02)
- Locks that serialise jobs: `task.configure(lock=<string>).defer(...)` or `@app.task(lock=...)`; "the second task cannot run before the first one has ended (successfully or not)"; order is priority, then creation time. Caveat in the docs: a locked job scheduled far in the future, or on a queue with no worker, blocks all later jobs with that lock. (source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/locks.html, checked 2026-09-02)
- Queueing locks (deduplication): `queueing_lock` "allows a single job in todo status"; deferring a second one raises `AlreadyEnqueued`, "which you can choose to ignore". Useful for the 3-second poller so only one poll job is ever waiting. (source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/queueing_locks.html, checked 2026-09-02)
- LISTEN/NOTIFY versus polling: both. The worker uses PostgreSQL `LISTEN` to be woken when a job is deferred, and falls back to polling every `fetch_job_polling_interval` (formerly `timeout`); `abort_job_polling_interval` controls how often abort requests are checked. "A worker will keep fetching new jobs as long as they have capacity to process them." (source: https://procrastinate.readthedocs.io/en/stable/discussions.html, checked 2026-09-02)
- Worker crash recovery: since 3.1.0 (2025-03-22) workers write a heartbeat every 10 seconds (default); a worker whose heartbeat is older than 30 seconds (default) "will be considered stalled" and its `doing` jobs are returned by `JobManager.get_stalled_jobs()`; `JobManager.retry_job()` re-queues them. The docs give a `@app.periodic(cron="*/10 * * * *")` task with `queueing_lock="retry_stalled_jobs"` that does exactly this. (source: https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html and https://github.com/procrastinate-org/procrastinate/releases/tag/3.1.0, checked 2026-09-02)
- Admin and monitoring: the Django models are registered in the Django admin (read-only list with filters, plus admin actions "Retry Job", "Cancel Job (only 'todo' jobs)", "Abort Job (includes 'todo' & 'doing' jobs)"). CLI: `procrastinate healthchecks` (config, DB connection, jobs table) and `procrastinate shell` (list jobs, tasks, queues, locks; retry and cancel a job). Web dashboard: "Not yet, maybe someday". (source: https://github.com/procrastinate-org/procrastinate/blob/main/procrastinate/contrib/django/admin.py, https://procrastinate.readthedocs.io/en/stable/howto/django/models.html, https://procrastinate.readthedocs.io/en/stable/howto/production/monitoring.html, checked 2026-09-02)
- Deployment guidance in the docs is thin: "While we know Procrastinate has been successfully deployed in production, the lib authors were not really involved in the process." Practical shape is one `manage.py procrastinate worker` process per container, restarted by Compose. (source: https://procrastinate.readthedocs.io/en/stable/howto/production/deployment.html, checked 2026-09-02)
- Maintenance activity: latest commit on `main` 2026-08-31 ("Lock file maintenance (#1622)"); more than 100 commits since 2025-09-02 (first API page full); nine releases in the last 12 months; about 1,375 stars; 89 open issues. (source: https://api.github.com/repos/procrastinate-org/procrastinate/commits and https://github.com/procrastinate-org/procrastinate, checked 2026-09-02)
- psycopg 3 and async: the core dependency is `psycopg[pool]` (psycopg 3); `psycopg2-binary` and `aiopg` are optional extras. "The worker can only be run with an asynchronous connector, but you can defer jobs with either asynchronous and synchronous connectors." Connectors: `PsycopgConnector` (async, psycopg 3), `AiopgConnector` (async, legacy), `SyncPsycopgConnector`, `Psycopg2Connector`, `SQLAlchemyPsycopg2Connector` (sync, defer only). (source: https://pypi.org/pypi/procrastinate/json and https://procrastinate.readthedocs.io/en/stable/howto/basics/connector.html, checked 2026-09-02)
- In a Django project the `DjangoConnector` defers jobs through Django's own database connection (whichever driver Django uses), but the worker is built by `get_worker_connector()`, which returns a `PsycopgConnector` "if psycopg3 is installed, otherwise an AiopgConnector", and raises `ImproperlyConfigured` "You must install either psycopg(3) or aiopg" if neither is present. `DjangoConnector.listen_notify` itself raises `NotImplementedError`; LISTEN/NOTIFY happens in the worker's psycopg 3 connection. Simplest path: run Django on psycopg 3 (Django 6.0 recommends psycopg 3.1.12+ and says psycopg2 support "is likely to be deprecated and removed"). (source: https://github.com/procrastinate-org/procrastinate/blob/main/procrastinate/contrib/django/django_connector.py and https://docs.djangoproject.com/en/6.0/ref/databases/, checked 2026-09-02)
- Task functions may be plain `def` or `async def`; async tasks can use Django's async ORM. (source: https://procrastinate.readthedocs.io/en/stable/howto/django/basic_usage.html, checked 2026-09-02)

## 2. Django's built-in Tasks framework (django.tasks) and django-tasks / django-tasks-db

- Shipped in Django 6.0, released 2025-12-03 (Python 3.12, 3.13, 3.14): "Django now includes a built-in Tasks framework for running code outside the HTTP request-response cycle." "Django handles task creation and queuing, but does not provide a worker mechanism to run tasks. Execution must be managed by external infrastructure, such as a separate process or service." (source: https://docs.djangoproject.com/en/dev/releases/6.0/, checked 2026-09-02)
- Backends in core: exactly two, `django.tasks.backends.immediate.ImmediateBackend` (runs the task at once, in-process) and `django.tasks.backends.dummy.DummyBackend` (stores, never runs). "Django includes only development and testing backends." No database backend and no worker command are in core. (source: https://docs.djangoproject.com/en/6.0/ref/tasks/, checked 2026-09-02)
- Production guidance from the topic guide: "Production systems should rely on backends that supply a worker process and a durable queue implementation. Available third-party backends are listed on the Community Ecosystem page." (source: https://docs.djangoproject.com/en/6.0/topics/tasks/, checked 2026-09-02)
- The Community Ecosystem "Background Tasks" list names: django-tasks-db ("ORM-based backend"), django-tasks-rq ("RQ-based backend"), django-tasks (the backport), and huey ("with Redis, SQLite and Postgres backends, usable from Django directly or as a backend for the Tasks framework"). (source: https://www.djangoproject.com/community/ecosystem/, checked 2026-09-02)
- Django 6.1 (released 2026-08-05) changed only small things in Tasks: `task()` accepts `**kwargs` forwarded to the backend's `task_class`, and `Task`/`TaskResult` can be pickled. Still no core worker. (source: https://docs.djangoproject.com/en/6.1/releases/6.1/, checked 2026-09-02)
- Task API (core and backport alike): `@task(priority=..., queue_name=...)`, `.enqueue(...)` returns a `TaskResult`; `run_after` delays a task; queue names can be restricted with `QUEUES`; `.attempts` "will currently only ever be 0 or 1" (that is, no automatic retries in the framework). (source: https://github.com/RealOrangeOne/django-tasks/blob/master/README.md and https://docs.djangoproject.com/en/6.0/topics/tasks/, checked 2026-09-02)
- django-tasks (RealOrangeOne), the backport for Django 4.2 to 6.0: latest 0.12.0, uploaded 2026-02-06; BSD-3-Clause; Python 3.10 to 3.14; classifier "5 - Production/Stable"; four releases in the last 12 months; last push to the repo 2026-05-22. "Prior to 0.12.0, django-tasks-db and django-tasks-rq were also included"; today it ships only the dummy and immediate backends. On Django 6.x it is not needed at all. (source: https://pypi.org/pypi/django-tasks/json and https://github.com/RealOrangeOne/django-tasks, checked 2026-09-02)
- django-tasks-db (the database backend, now a separate package): latest 0.13.0, uploaded 2026-08-28 (only other release 0.12.0, 2026-02-06); BSD-3-Clause; requires `django>=5.2` (a `compat` extra pins Django 5.2 with django-tasks); classifier "Development Status :: 4 - Beta". Configure `TASKS = {"default": {"BACKEND": "django_tasks_db.DatabaseBackend", "QUEUES": ["default"]}}`. (source: https://pypi.org/pypi/django-tasks-db/json and https://github.com/RealOrangeOne/django-tasks-db/blob/master/README.md, checked 2026-09-02)
- Worker command: `./manage.py db_worker` with `--queue-name`, `--exclude-queues`, `--interval` (seconds to sleep when the queue is empty), `--batch`, `--max-tasks`, `--worker-id` ("MUST be unique across worker pool"), `--reload` (dev only), `--no-startup-delay`. The loop claims a task with `select_for_update(skip_locked=True)` then runs it in the same process before looking for the next; run several `db_worker` processes for parallelism. Also `prune_db_task_results` for retention. (source: https://github.com/RealOrangeOne/django-tasks-db/blob/master/django_tasks_db/management/commands/db_worker.py, https://github.com/RealOrangeOne/django-tasks-db/blob/master/django_tasks_db/models.py, https://github.com/RealOrangeOne/django-tasks-db/blob/master/README.md, checked 2026-09-02)
- Features flagged by the backend: `supports_defer` (run_after), `supports_async_task`, `supports_get_result`, `supports_priority` all True. Retries: none (see `.attempts`). Periodic or cron tasks: none; only `run_after`. Crash recovery of a task stuck in RUNNING after a worker dies: nothing found in the README or the backend (unverified). Admin: `DBTaskResult` registered read-only in the Django admin with status, queue and priority filters. (source: https://github.com/RealOrangeOne/django-tasks-db/blob/master/django_tasks_db/backend.py, https://github.com/RealOrangeOne/django-tasks-db/blob/master/django_tasks_db/admin.py, https://github.com/RealOrangeOne/django-tasks/blob/master/README.md, checked 2026-09-02)
- Stated production readiness: the Django docs call the core backends dev/test only and defer to third parties; django-tasks-db describes itself as "A Django Tasks backend which uses Django's ORM to store tasks in the database" and the ecosystem page says "suitable for simple background task processing"; its PyPI status is Beta. (source: https://www.djangoproject.com/community/ecosystem/ and https://pypi.org/pypi/django-tasks-db/json, checked 2026-09-02)

## 3. Huey

- Latest release: 3.3.4, uploaded to PyPI 2026-08-05 (GitHub release the same day). Sixteen releases between 2025-09-02 and 2026-09-02 (2.5.4 on 2025-10-23 through 3.3.4), including the 3.0.0 major on 2026-04-14. (source: https://pypi.org/pypi/huey/json and https://github.com/coleifer/huey/tags, checked 2026-09-02)
- Licence: MIT (repo LICENSE, "Copyright (c) 2017 Charles Leifer"; GitHub API reports MIT). Note: the PyPI listing carries no licence classifier or licence field, so the licence is verified from the repository only. (source: https://raw.githubusercontent.com/coleifer/huey/master/LICENSE and https://pypi.org/pypi/huey/json, checked 2026-09-02)
- Backends: "support for redis (or valkey/redict), postgres, sqlite, file-system, or in-memory storage". Classes: `RedisHuey` (default; also priority and expire variants), `SqliteHuey` ("Only requirement is the standard library sqlite3 module"), `CySqliteHuey`, `PostgresHuey` ("utilizes PostgreSQL for queue, schedule and result storage. Requires psycopg 3.2 or newer"), `MemoryHuey` ("Only should be used when testing or when using immediate mode"), `FileHuey` ("Should not be used in high-throughput, highly-concurrent environments"). Base install has no dependencies; extras `huey[redis]`, `huey[postgres]`. (source: https://huey.readthedocs.io/en/latest/ , https://huey.readthedocs.io/en/latest/api.html , https://huey.readthedocs.io/en/latest/installation.html, checked 2026-09-02)
- Postgres backend and several consumers: "Workers dequeue using select ... for update skip locked, so any number of consumers, on any number of hosts, can share a queue without contending for the same rows." Whether `PostgresHuey` uses LISTEN/NOTIFY or polls: unverified (the consumer page names only the SQLite and file backends as polling). (source: https://huey.readthedocs.io/en/latest/guide.html and https://huey.readthedocs.io/en/latest/consumer.html, checked 2026-09-02)
- Django integration: `huey.contrib.djhuey` in `INSTALLED_APPS`, a `HUEY` settings dict (`huey_class`, `connection`, `consumer` with `workers`, `worker_type`, `periodic`, and so on), consumer started with `./manage.py run_huey` (`-w/--workers`, `-k/--worker-type`), decorators `task`, `periodic_task`, `db_task` (closes DB connections), `db_periodic_task`, `on_commit_task`; `tasks.py` auto-discovery. (source: https://huey.readthedocs.io/en/latest/contrib.html, checked 2026-09-02)
- Django admin and Django 6.0 Tasks: adding `huey.contrib.djhuey.stats` gives an admin dashboard (queue monitoring, throughput, revoke/restore); `huey.contrib.djhuey.tasks_backend.HueyBackend` lets Huey act as the backend for `django.tasks`. (source: https://huey.readthedocs.io/en/latest/contrib.html, checked 2026-09-02)
- Periodic tasks: `@huey.periodic_task(crontab(minute='*/3'))`; `crontab()` takes minute, hour, day, month, day_of_week. Rule with several consumers: "only one consumer should be configured to enqueue periodic tasks. All other consumers should be started with the -n / --no-periodic flag. Without this, each consumer will independently enqueue the same periodic tasks, leading to duplicate executions." (source: https://huey.readthedocs.io/en/latest/guide.html and https://huey.readthedocs.io/en/latest/consumer.html, checked 2026-09-02)
- Retries: `@huey.task(retries=2, retry_delay=10)`; `retry_backoff=2` gives exponential back-off ("retried after 10 seconds, then 20, then 40"). (source: https://huey.readthedocs.io/en/latest/guide.html, checked 2026-09-02)
- Worker modes and concurrency: `-w/--workers` "Number of worker threads/processes/greenlets. The default is 1"; `-k/--worker-type` "thread, process or greenlet. The default is thread." Troubleshooting page: "For CPU-bound tasks, use -k process." So four ffmpeg jobs at once would be `-w 4 -k process` (or threads, since ffmpeg runs as a subprocess). (source: https://huey.readthedocs.io/en/latest/consumer.html and https://huey.readthedocs.io/en/latest/troubleshooting.html, checked 2026-09-02)
- SQLite backend with several worker processes: the docs say WAL mode "enables readers to coexist with a single writer", there is a busy `timeout` (default 5 s), "SqliteHuey may be a good choice for moderate workloads where the operational complexity of running a separate server process like Redis is undesirable", and for containers "SqliteHuey and FileHuey work across containers only if every container mounts the same local volume, and sqlite over a network filesystem is a bad idea". No sentence explicitly blesses or forbids several consumer processes on one SQLite file (unverified). Since Postgres is already in the stack, `PostgresHuey` makes this moot. ## 7. A hand-rolled Postgres poller in Django

- `QuerySet.select_for_update(skip_locked=True)` exists; `nowait` and `skip_locked` are mutually exclusive (ValueError); "The postgresql, oracle, and mysql database backends support select_for_update()"; "Evaluating a queryset with select_for_update() in autocommit mode ... is a TransactionManagementError", so the claim query must sit inside `transaction.atomic()`. (source: https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update, checked 2026-09-02)
- Added in Django 1.11 (released 2017-04-04): "Added the skip_locked argument to QuerySet.select_for_update() on PostgreSQL 9.5+ and Oracle to execute queries with FOR UPDATE SKIP LOCKED." (source: https://docs.djangoproject.com/en/5.2/releases/1.11/, checked 2026-09-02)
- PostgreSQL added it in 9.5.0 (released 2016-01-07): "Add SELECT option SKIP LOCKED to skip locked rows (Thomas Munro)". Current docs: "With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." Django 6.0 supports PostgreSQL 14+, so any supported Postgres has it. (source: https://www.postgresql.org/docs/release/9.5.0/, https://www.postgresql.org/docs/current/sql-select.html, https://docs.djangoproject.com/en/6.0/ref/databases/, checked 2026-09-02)
- django-tasks-db is itself a small example of this pattern (`select_for_update(skip_locked=True).first()` then `claim(worker_id)`), which shows what the primitive buys and what it does not. (source: https://github.com/RealOrangeOne/django-tasks-db/blob/master/django_tasks_db/models.py, checked 2026-09-02)
- What a home-grown poller still has to build and test itself (these are design facts, not sourced claims): a job table and state machine (todo, doing, done, failed); a claim query in a transaction; a polling loop with a sleep interval (Postgres LISTEN/NOTIFY wake-ups are extra work); retry counting and back-off; one-off scheduling (`run_after`) and cron-style periodic jobs with "only once per period even with two workers" protection; detection of jobs whose worker died (heartbeat or lease timeout) and their re-queue; graceful shutdown on SIGTERM; an admin page; and log/metrics. Procrastinate ships each of these already (section 1).

## 9. Gunicorn vs uvicorn for Django

- Gunicorn sync workers (current design page; the old docs.gunicorn.org URL now 404s): "The default worker. Handles one request at a time per worker. Simple and predictable. Errors affect only the current request. No keep-alive support (connections close after response). Requires a buffering proxy (nginx, HAProxy) for production." Async workers are needed for "Streaming request/response bodies", "Long polling or Comet patterns", "WebSockets". Decision guide: "Simple app behind nginx? -> sync (default) ... WebSockets, streaming, long-polling? -> gevent or ASGI worker." Worker count: "workers = (2 x CPU cores) + 1" and "Gunicorn typically needs only 4-12 workers". (source: https://gunicorn.org/design/, checked 2026-09-02)
- Practical consequence for SSE: with sync workers every open event stream occupies one worker for its whole life, so on a 4-core host (9 workers by the formula) nine open status pages would stop the site answering anything else. That is the constraint the Django docs describe as "tie a worker process for the entire duration of the response". (derived from the two bullets above and section 8)
- Gunicorn now has a native ASGI worker (`--worker-class asgi`, beta in 24.0.0 of 2026-01-23, HTTP/2 in 25.0.0). Latest gunicorn 26.2.0, uploaded 2026-08-24; MIT. (source: https://gunicorn.org/asgi/ , https://gunicorn.org/news/ , https://pypi.org/pypi/gunicorn/json , https://raw.githubusercontent.com/benoitc/gunicorn/master/LICENSE, checked 2026-09-02)
- Uvicorn: 0.52.4, uploaded 2026-08-19; BSD-3-Clause; Python >=3.10. Its docs: "Gunicorn is probably the simplest way to run and manage Uvicorn in a production setting", but "The uvicorn.workers module is deprecated" (since 0.30.0, 2024-05-28); use the `uvicorn-worker` package (0.4.0, 2025-09-20, BSD-3-Clause): `gunicorn myproject.asgi:application -k uvicorn_worker.UvicornWorker`. (source: https://pypi.org/pypi/uvicorn/json , https://raw.githubusercontent.com/Kludex/uvicorn/master/LICENSE.md , https://raw.githubusercontent.com/Kludex/uvicorn/master/docs/deployment/index.md , https://pypi.org/pypi/uvicorn-worker/json, checked 2026-09-02)
- Django's own ASGI deployment docs list Daphne, Hypercorn and Uvicorn, and the Uvicorn page shows exactly that gunicorn plus `uvicorn_worker.UvicornWorker` command for production ("process monitoring and automatic restarts"). (source: https://docs.djangoproject.com/en/5.2/howto/deployment/asgi/ and https://docs.djangoproject.com/en/5.2/howto/deployment/asgi/uvicorn/, checked 2026-09-02)
- Net: keep gunicorn sync workers if the UI uses HTMX polling only; switch the web container's command to gunicorn with the uvicorn worker (or plain uvicorn) before adding SSE. Either way it is one container.
