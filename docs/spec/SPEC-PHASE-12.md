# Gideon Transcribe, Phase 12 specification

The cameras on a map. A body-worn or in-car camera's export puts a small text file beside the video that says where the camera was, second by second, and what its switches were doing; the app keeps that file on the Recording as its Path file, reads it once, and draws every camera of a Case on a street map on one clock, with the video a press away and the readings answerable by Gideon anywhere in the Case. Five releases; this document holds chapter 1, the first.

## About this document

This is the build specification for Phase 12 of Gideon Transcribe. On 2026-11-02 the maintainer asked: "for some body worn camera video we receive a separate file that contains metadata related to the recording. In the metadata there's location data that tracks the movement of the officer ... there could be a separate tab in a case that utilizes that file to show the movement on a map dynamically ... users should be able to click on a camera and have that play along with it ... I want smart use of data. There's good data in these files ... chat anywhere within a case should be usable. For example when were the lights triggered or turned on. When did officer so and so turn their body camera recorder on/off ... the user should be able to add notes from this maps tab ... I want users to be able to toggle a larger view of the map ... toggle the trail movement ... click and select events." The design was worked through the same day and drawn in `docs/spec/mockups/phase-12-map.html` (figures A to L, fifteen choices), which the maintainer agreed stands. The maintainer's four answers: the street map in the first release; the word is Path; the camera's clock comes from the file, then the app's clock, then the file's name; path files come in through the Map tab only. The joins chosen from the fifteen offered: 1, 2, 4, 5, 6, 8, 9, 10 and 11.

It builds on Phase 6 (Incidents and their clock), Phase 8 chapter 2 (Notes), Phase 9 (People), Phase 10 (the case's chronology, the Recording's clock, ADR 0027, the Incidents tab's strip) and Phase 7 chapter 5 (Ask Gideon). ADR 0029 records the decisions that are hard to reverse.

Read it with `CONTEXT.md` (Path, Fix, Path file, Map, Basemap), `docs/spec/ADMIN-SETTINGS-CATALOGUE.md` (the Maps row) and `docs/adr/0029-the-cameras-path-is-kept-on-the-recording-and-the-map-is-drawn-from-a-file-the-office-holds.md`. `docs/research/path-file.md` is the file's format as learnt, and `docs/research/basemap.md` the street map's facts, pins and hashes.

Nothing in this document is office-specific. The sample readings here are invented, from the demo office, with the fixes in the open Atlantic. No new environment key and no new service; one setting (Maps), one folder under the app data folder, one file the Admin places.

## 1. The cameras on a map

### Principles

1. **The file is the camera's record, and the app invents no position.** Where the file has no fix, the map draws nothing and says "no fix". Nothing is interpolated across a gap; between two fixes within ten seconds the marker moves in a straight line, which is how a reading a second apart is drawn, not a guess.
2. **A Path belongs to its Recording.** One file per video, kept in the recording's folder beside the playback copy, counted in its size, gone with it, never served to a browser.
3. **Nothing reaches outside the office.** The drawing library is in the app's static files; the streets come from one file the Admin placed on the server, served by the office's own server to signed-in browsers; the app never fetches a tile.
4. **Positions are content.** A camera's fixes, the wearer's name, the unit and the department are never in an audit row, a log line, an export or the engine's reading. Gideon is told times of day, distances between cameras and the readings' words, never a coordinate.
5. **One clock, one day at a time, the office's time of day.** The same clock the incident page and the case's chronology run on; a camera off the clock is listed and can be shown on its own, never guessed onto it.
6. **The same words, gestures and places the office has met.** The Preview is the player; the strip is the incident page's; a note from the map is a note on the recording like any other; an incident from the map is the Incidents tab's own Make it.

### Words

**Path**, **Fix**, **Path file**, **Map** (the tab) and **Basemap**, as `CONTEXT.md` defines them. The pages say "path", "fix", "no fix", "path file", "street map" and never track, route, GPS, ping, waypoint, sidecar, tiles or tile server.

### The path file

What the exporting cameras write, as learnt from the office's own files (`docs/research/path-file.md`, counts only):

- A WebVTT file (`WEBVTT` first; cues of `HH:MM:SS.mmm --> HH:MM:SS.mmm`, one a second) named as the video is named with the ending `.vtt`. Each cue's text is one JSON object.
- Every reading carries `gpsCoordinates` ("N36.123456 W86.123456", or "" when the camera had no fix), `mic` (0 or 1), `low battery`, `officer` (the wearer's name as the department spelt it), `vehicle` (the unit id), `department` and `eventDate`.
- A **body-worn** camera's `eventDate` is empty, and its `mic` turns on about sixty seconds into every file: the camera keeps the minute before the officer activates it, without sound. So the reading's words are "activated at 20:27:05 (the minute before is the camera's buffer, without sound)", and "camera on" is the buffer's start.
- An **in-car** unit's readings also carry `eventDate` as its own wall clock ("11/06/25 14:20:03", the exporting office's local time), `patrolSpeed` with `speedUnit`, and the switches `lights`, `siren`, `brakes`, `crash`, `aux` and `bookmark` as 0 or 1. One unit exports one file per stream (front, cabin, rear), identical.
- The file name's twelve-digit stamp (`_YYYYMMDDHHMM_`) is the recording's start to the minute in UTC: in every sample it sits one zone's offset from the clock inside.

The parser (`core/camera_paths.py`, `parse()`) is pure and refuses with plain words: not WebVTT; no cue with a camera reading; a reading with neither a position nor a camera flag; over 20 MB; over 50,000 cues. It reads a byte-order mark, CRLF endings, a cue identifier line, a zero-length cue, and skips a cue whose JSON will not parse (counted as unread). The source is `car` when the first reading carries `patrolSpeed`, `lights`, `siren` or `brakes`, else `body`. Fixes are kept to a tenth of a second and six decimal places, repeats collapsed; a stretch with no fix over ten seconds is a gap; each flag's first value and every change is a mark; an in-car speed is a mark on change. A file with no fix at all is kept for its readings (one of the office's twenty-six samples is such a file, a camera indoors throughout, and it still says when the officer activated it).

### Taken in

- **From the Map tab only** (the maintainer's answer): **Add path files** in the tab's head takes a folder's worth of files in one post (`POST case/<id>/paths/add`). Each file whose name matches exactly one video of the case that has no path file lands on it at once; the answer says what landed ("12 files added to their videos") and lists the rest to settle in a Layer: **flagged** (the name matched, but the unit inside disagrees with the camera id the picture's clock named, or the length differs from the video's by over a tenth, or the minute in the name sits over an hour from the recording's clock), with Add anyway; **has one** (the video already has a file), with Replace; **unmatched** (no video of that name), with a chooser of the case's videos and the file described in a few words ("A body camera, 38 minutes, 6 Nov 2025 by its name"); **refused**, with the reason. Settling posts the same endpoint again with the chosen recording ids. (Amended by chapter 6, v1.194.0: Add path files moved to the case's head, and an unmatched file waits on the case for its video instead of being settled with a chooser.)
- **On a row**: a video without a file has **Add a path file** (`POST recording/<id>/path`); a camera's "..." offers Replace and Remove (`POST recording/<id>/path/remove`). A mismatched name is taken with a warning; a second file replaces only when asked.
- **Who may**: anyone who may open the recording (`cases.standing`), so the owner, a collaborator and an Admin; while Maps is off the endpoints are 404 and files already there stay.
- The file is written into the recording's folder as `path.vtt`, the recording's disk measured, one audit row written (Appendix A), the case's activity noted. The parse runs in the request: the slowest of the office's files reads in a tenth of a second.

### What is kept

`CameraPath`, one per Recording (migration 0103): the source, the wearer, the unit and the department as the file gives them; the in-car clock's start in the office's zone and whether the first and last dated cues agree within two seconds; the fixes, the marks, the gaps, the speed unit; the counts (cues, unread, fixes), the first and last fix, the length, the bounds; whether the stem matched; the state, the error and the read version (a later parser re-reads the kept file on the media queue, as Documents do); the file's name, its size, who added it and when. The file itself is `path.vtt` in `Recording.folder`.

### The camera's clock

For the map, in the maintainer's order (`zero_of`): (1) the path file's own clock, surety **Clear** when the first and last dated cues agree and **Likely** when they do not; (2) the clock the app holds for the recording (ADR 0027: from the stamp, by hand, from the file, by sound), with its own surety word; a day alone is not a zero and the camera is listed under its day as not on the clock; (3) the file's creation time from the probe, **Unchecked** (the build's addition within the rules: it is seconds-precise and the chronology already offers it); (4) the minute in the file's name, read as UTC and shown in the office's time, **By its name** in the warning tone; (5) none: the camera is off the clock, listed under every day with **Show on its own**. In this release the path file's clock is read for the map alone and places nothing on the case's chronology; release 2 amends ADR 0027 for that.

### The Map tab

Between Incidents and Clips in the case bar, with the count of cameras that have a path file; present while Maps is on. One reading, `GET case/<id>/map.json` (optional `?day=`), never polled, read again after a change: the time zone, the basemap's state, the days with their camera counts, the cameras (id, title, unit, wearer, source, colour as the chronology colours the recording, the zero with its surety, the day alone, the length, the fixes, the marks, the gaps, the events, the notes, the clips, the playback address, the recording page, the incident, the twin), the cameras off the clock, the videos without a file, the incidents with their cameras and dates, the forming offer, the note endpoint.

- **The day.** Chips for every day on which a camera is on the clock, each with its camera count and, where the Incidents tab knows one, its incident count; the day with the most cameras opens first; `?day=` keeps the choice in the address. The clock runs one day at a time; a camera past midnight belongs to the day it started.
- **The lead.** How many cameras and how many with a path file; the Show control (**Markers only**, **Trails**, **Whole paths**, remembered per person); the Events ticks (camera on and off, lights, siren, mic, bookmarks, notes) choosing what is drawn on the map and the lanes; the transport (Play, −10 s, +10 s, ‹ event, event ›, Speed 1/4/16/60, the clock with the zone name and the day, Fit all, Note here, Larger map). Amended by 6.8 (v1.208.0): one bar with More, the Show choice and the ticks in the map's corner, the explanation behind a ?, Larger map gone.
- **The map.** The street map from the basemap when it is installed, in the page's light or dark flavour, swapped when the theme changes; plain ground otherwise, with a line saying so and that the Admin can install one. Every camera's whole path faint, its trail to the clock's moment in its colour, a marker where it is now (round for a body camera, square for an in-car unit, its unit id on it, dimmed in a gap, hollow after it ended, with a badge for lights and siren), and pips where the ticked events happened. Zoom and pan freely; rotation is off and north is up. The browser's full screen from the map's corner, with a slim bar (play, clock, speed, Leave full screen).
- **The list.** Beside the map at 1024 and up, under it narrower: "N of M in view" from the map's bounds, the rest folded; a row with the camera's colour, unit, wearer, surety pill, its span on the clock, body or in-car, no position where the file has none, **Play here**, and the "..." for Replace and Remove; hover lights the path, a press flies to it; the cameras not on the clock under their own fold with **Show on its own** (the path lit with its own bar); other days' cameras folded; the videos without a file last with Add a path file. The forming offer was a card at the foot of the list until v1.197.0; from v1.198.0 a suggestion is a card on the Incidents tab and nothing on the map (chapter 6, part 6.6).
- **The strip.** The incident page's lanes: a ruler of the day's span, a lane per camera on the clock with its bars (segments of fixes), its gaps thinner, its clips along the top in the clip colour, its events as marks (lights and siren with their on-spell drawn), its notes, the camera's speed in the lane head while it moves; the playhead draggable by mouse or touch. Amended 2026-11-10 (v1.227.0, at the maintainer's word, from the drawing `docs/spec/mockups/phase-12-map-lanes-look.html`, T1 and N2): the playhead's clock is a flag in the ruler row, inside the sticky ruler and above its labels, at the small text size, to the second, kept inside the ruler at either end with its pointer on the line, and the line has a hairline edge in the page's background; a note on a lane is the folded-corner tag the incident page's strip uses, in the page's ink with an edge in its background, the lane's height and 8 px wide, its straight left edge at the note's moment; and the ruler sticks at the lanes heading's own measured height (it stuck at a fixed 33 px under a 39 px heading, which cut its labels and the clock when the lanes scrolled). Amended 2026-11-10 (v1.228.0, at the maintainer's word, from the drawing `docs/spec/mockups/phase-12-map-lanes-piles.html`, P1): notes on a lane that would overlap stand as one pile, a tag 15 px wide (19 px from ten notes) with a second leaf behind it and their number on it, at the first note's moment; a note joins a pile when it would stand within 20 px of the pile's first note, so a busy stretch is a row of piles, and the piles re-form whenever the lanes are drawn or change width. A press on a pile opens chapter 6's list of pips on one spot, set on the map's lower edge above the pile and headed "N notes here", each line the note's time, its words and who wrote it; a line's press opens that note's card, which says "k of N here" with its steps, and the pile takes the selection's outline. Pointing at a pile names its count and its first and last times. Found on the way and fixed: the strip was wired again at every redraw, so each press on a mark redrew the lanes twice as many times as the press before; it is wired once.
- **The Preview as the player.** A marker, Play here or a row opens the Preview's window on that camera at the clock's moment exactly (no ten-second lead-in; `exact`), and the transport reads "following BWC2-1": while the window plays, every marker moves with the video, and a seek on the strip seeks the video. Closing the window leaves the clock where it is. A two-stream in-car unit is one marker and one row with its streams named.
- **The events.** A press on a pip or a lane mark selects it: the clock moves there, the camera lights, a card beside the pip says what, when (and the street, read from the basemap's own labels in the browser, when there is one), until when, with **Play here**, **Add a note**, **Clip from here**, the camera's previous and next, and Close; ‹ event and event › on the transport step every shown event of the day in order; Escape clears. A note pip opens the same card with the note's words, who wrote it, **Edit** (the recording page with the note lit) and **On the Notes tab**.
- **Notes from the map.** **Note here** on the transport writes a note on the selected camera at the clock's moment; **Add a note** on an event's card at the event's moment. Both go through the recording's own note-at-a-moment endpoint (v1.99.0) and are the recording's notes: on the Notes tab, in the exports, an event on an incident's chronology where the camera is synced. Nothing new is kept.
- **The keyboard.** Space plays and pauses; Left and Right step a second, ten with Shift; Escape clears the selection; the Preview's keys are its own.
- **Narrow screens.** One column under 1024; under 900 a slim bar with play, the clock and the speed stays above the Preview's sheet; under 700 the lane heads narrow and the rows become cards.
- **Without WebGL.** The constructor's failure is caught: "This browser cannot draw the map"; the list and the strip still work.
- **Not on the clock.** A camera with no zero has no lane and no marker on the shared clock; **Show on its own** draws its path with its own range control, and Play here opens the Preview at that point.

### Gideon knows the readings

The case chat (`case_chat.answer_case_turn`) appends a readings block beside the placements block for every recording the question reads that has a path file: one paragraph per camera in the office's time of day, "Recording 3 (BWC2-1; a body camera, worn by the wearer as the file gives it; clock from the minute in its file name): recording began 14:20:03; activated 14:21:04 (the minute before is the camera's buffer, without sound); no fix 14:31:10 to 14:36:00; stood still 14:45:00 to 14:51:00 (6 minutes); recording ended 14:58:11." and for an in-car unit "lights on 14:22:08 to 14:31:40; siren on 14:22:08 to 14:26:30; brakes 14:26:28; bookmark pressed 14:30:01; reached 41 mph 14:24:10"; then which cameras were within 50 m of each other and when. A rule joins the system message, as the Documents rule does: the readings come from the camera's own file, say which camera, give the time of day, cite the moment as [Recording N, HH:MM:SS]. The incident chat gets the same block for its cameras, by the incident's clock where the camera is placed on it. So "when were the lights turned on", "when did the officer turn the camera on" and "who was near the vehicle at 14:30" are answered from the readings alone, and a cited moment opens the Preview as any citation does. A camera not on the clock is told in minutes into the recording. Coordinates are never in the prompt. The chat's audit row is unchanged.

**Amended 2026-11-12, v1.235.0: the case chat's sheet rewritten, and a question about the files answered from the files.** From the maintainer's trial on an office's case with 89 path files, asked "when did [an officer] turn his lights on" and then "who was nearby when the lights came on". Three faults showed, each in this section as written. The time was right and its reference opened nothing: the readings were worded in the time of day and the rule asked for `[Recording N, HH:MM:SS]`, so the engine wrote the time of day as the reference, hours past the recording's end. The answer took 2 minutes 54 seconds, ninety transcripts in six Readings, because the block went with every Reading. And the second answer was the Readings arguing, by name ("Part 2 states..."), each having read 326 lines of pairs its own way. What changes, for the case chat alone (the incident chat, the memo, the comparison and the timeline report keep their block):

- **The sheet.** One line per reading, each followed by its reference into the recording, ready to copy: "- lights on 14:22:08 [Recording 35, 00:01:05] to 14:31:40." For the lights, the siren, a camera being activated, a bookmark and the crash sensor the line then says who was near at that moment, worked out by the app from the files' positions: "Within 50 m then: nobody else's camera. Nearest beyond: officer Ruiz 120 m, unit 7 (officer Tan) 310 m." (the nearest two beyond 50 m and inside 2 km). Cameras are named by officer and unit, an officer with two cameras is said once, and an officer's own cameras, or one unit's two streams, are never "someone nearby". The lines of pairs become, under each camera, who was within 50 m of it for a minute or more and when, by name. Never a coordinate, as before.
- **The rule** the case chat is given with the sheet says the reference is given with the reading and is never a time of day, and that who was near is written with the reading and is not to be worked out again.
- **A sorting step.** Where the recordings a question may read include a camera with a path file, one small call (the question and the three before it, a schema, no thinking) sorts it: the files alone, the transcripts, or both; anything but a clear answer is both. A case with no path file is asked nothing more.
- **The files alone**: one call with the sheet for everything the question may read and no transcript, so it is seconds and does not depend on the hours ceiling or on which recordings the overviews would point to; the route is `files`, the line under the answer reads "Read the cameras' own files, 6 s", the audit row's feature is `case_chat_files` so the time expectation of a whole-case question is not skewed by it, and the answer has no opening line. Where a very large case's sheet would not fit a Reading it is sent without the spells of nearness. If the files do not hold the answer the engine says exactly that and the question is read as "both", in the same turn.
- **The transcripts**: the question is read as before and the sheet is not sent at all.
- **Both**: one Reading with room for it carries the sheet beside the transcripts. Read in parts, the parts go without it, and the combining call alone is given it, once, after the part answers, with leave to add the references that follow a reading there.
- **The combining call never names its parts**, whatever the question: one answer, in one voice.
- **A case with no path file among what a question reads** (Maps on): one sentence joins the system message, so a question about lights, a siren, a camera being activated or who was near is answered "no camera in this case has a file that records it" and from what was said or shown, not "the transcripts do not say".

The audit row gains `sorted_as` (files, transcripts or both) where the step ran; never a word of the question. Left for later releases, each at the maintainer's word: Search finding readings, a line of status in the Preview, and the officers who were near first in the speaker picker.

### The basemap

One file, `<app data folder>/maps/basemap.pmtiles`, no setting and no path to type. It gets there one of two ways (amended v1.232.0, below): `./transcribe basemap fetch` fetches it on the server, or the Admin cuts a region of the free OpenStreetMap-based Protomaps builds on a workstation with the internet (`pmtiles extract` with a bounding box; the admin guide and `docs/research/basemap.md` give the command) and places it with `./transcribe basemap <file>`, which checks the file's first bytes, copies it under the app's account at 0640 and says so; `./transcribe basemap remove` takes it out. Caddy serves it from a third read-only root, `/maps/*`, behind the same forward_auth as the recordings (`/maps-auth`: 401 for nobody, 404 while Maps is off or for any other name, 200 for a signed-in person, no audit row, since the map is a public map of the region and not content), with byte ranges and `Cache-Control: private, max-age=604800` (a browser reads the file in small ranges on every pan and may keep them privately; the recordings' `no-store` stays theirs). `caddy/check-ranges.sh` proves the ranges on this route too. The Status page says whether the file is in place with its size and date. The drawing library (MapLibre GL JS 5.24.0), the PMTiles reader, the two Protomaps styles, three Noto Sans glyph stacks (eight ranges each) and the sprites are vendored in the app image's static files with their hashes in `app/static/vendor/README.md`. No CSP exists today; one added later must allow `worker-src blob:` for the library's worker.

**Amended 2026-11-12, v1.232.0: the street map fetched with one command.** The maintainer's words: offices across the entire United States will use the app, and the territories, Puerto Rico and Guam among them, must be in it. Until now this section said the file was cut on a workstation for the office's own region; that way stays, and beside it `./transcribe basemap fetch` does the work on the server, at an Admin's command and never the app's:

- **What it offers.** The whole United States and its territories (the 50 states, the District of Columbia, Puerto Rico, the US Virgin Islands, Guam, the Northern Mariana Islands and American Samoa; about 20 GB, measured), or only the states and territories the Admin names, by two-letter code or by name (0.1 to 1.5 GB each). The whole country is the usual answer where it leaves the app data folder the free space the app keeps; the five territories are always inside it, and each can be named alone. Full street detail only. Areas may also be given with the command (`basemap fetch US`, `basemap fetch CO PR GU`).
- **The areas are rectangles** with a margin of a tenth of a degree, so a path that crosses a state line or the border has its streets: the lower 48 with the District as one, and Alaska (two, split at the date line), Hawaii and each territory by its own. The table is in the script; a test holds it to the 50 states, the District and the five territories.
- **It looks before it fetches.** It says whether the server reaches `build.protomaps.com`, the newest build's date (the newest of the last eight days; Protomaps keeps a week), the room in the map folder and what map is in place. It works out the real size with the tool's dry run and says it; stops when the folder has not that with 5 GB to spare; and where the fetch would leave the app data folder under `DATA_GB_TO_KEEP` says so and makes no its usual answer.
- **The fetch.** Protomaps' own tool (`protomaps/go-pmtiles`, an upstream image pinned by tag and digest in the script, no part of the Compose stack) runs once as a container under the app's account with the map folder alone mounted, and cuts into a file beside the map. The map in place stays until the new file is known whole (its first bytes, which the tool writes last); a failure at any point removes what was begun and changes nothing. The build cannot be pinned, there being a new one each day and none kept past a week; its date is recorded instead.
- **The note.** The command leaves `maps/basemap.json` beside the file (the areas' codes, their words, the build's day). The Status page's line reads it: "installed, 19.0 GB, the whole United States and its territories, build of 11 Nov 2026, placed 12 Nov 2026"; a file placed by hand has no note and reads as before, and placing by hand or removing takes the note away. The map's route serves the one file and never the note. A second run offers "the same again, from the newest build" first.
- **Around it.** The install does not fetch the map; `bring-up` names the command at its end while no map is in place. The wider check names the host before an install only, as a note and never a stop. Nothing at run time changes: the app never fetches the map, the route, its sign-in rule and its cache header are as above, and no audit row is written. The nightly backup does not carry the map; the command fetches it again after a restore.
- **What the host learns** is what any download shows: the server's internet address and which parts of a public map were read. Nothing of a case, a recording or a person is sent.

Nothing is made without a press.
2. **Counts.** Home's case card carries "N cameras on the map" among its pills; the Details tab's About this case says "N cameras with a path file, M videos without"; the Status page says whether the street map is installed.
4. **Search, notes and proposed events.** **on the map** beside a search hit, a Notes tab row, and a case's chronology or Proposed events entry opens `?tab=map&recording=<id>&at=<seconds>`: the tab on that camera's day at that moment, the camera selected and in view.
5. **Clips.** A camera's clips sit along the top of its lane, pressable to play in the Preview; **Clip from here** on an event's card opens the recording page at that moment with the Clips tab ready, the way a clip starts from a line.

### What is not

No live positions and no address lookup: the app knows the streets only as the basemap draws them, and names one only in the browser from the basemap's own labels. No export of a path and no picture of the map until release 5. Nothing is told to Gideon but the readings' words and times. The path file's clock does not place a recording on the case's chronology until release 2. A Readings list, Offer to the chronology and Who was near here are release 3.

## 2. The path file's clock, and the readings beside the record (the second release, v1.188.0)

### The path file's clock places the recording

An in-car unit's path file carries the unit's own wall clock on every reading (chapter 1). When such a file is added to a recording that nothing has placed on the case's clock, the recording is placed from it: `clock_how` **path**, the date and the second of the day from the first dated cue less its offset, in the name of the person who added the file, with the usual "recording placed on the clock" row (how `path`). The rules of ADR 0027 bend by this much and no more (its amendment of 2026-11-02): the stamp still wins; anything a person chose (by hand, by the day, from the file's time, by sound) stands; the path clock takes only a recording with no clock at all, or one its own forerunner placed. Removing the file takes the clock with it ("recording taken off the clock"); replacing the file places afresh. The surety word is **Clear** when the file's first and last readings agree within two seconds and **Likely** otherwise, with the chapter 1 words; the chronology's pill reads "from its path file, <who added it>". A body camera's file carries no clock and places nothing. No migration.

### The readings beside the record

The memo's facts sheet and the comparison with the report are given each camera's readings beside the incident record, as the incident chat is (chapter 1): one line per camera with a path file, in the time of day, placed after the record and before the report's pages, with the readings rule joined to the system message. So a claim in the report about the lights, the siren, a camera turned off or a vehicle stopped is read against the file that knows, and the facts sheet can give the moment the officer activated the camera without the picture. The second pass of the memo is unchanged: it writes from the sheet alone. The timeline report prints **The cameras' own files** after the cameras' table, one bulleted line per camera, with a note saying what the lines are read from and that a body camera keeps the minute before activation without sound. Never a position in any of them.

**Amended 2026-11-12, v1.235.0: a path file that arrives after the writing.** The maintainer's question: what if a path file is added after the summaries and everything else are written? What a page reads from the files (the Map, a new chat question's sheet, where a line was said, the picker's names) is read afresh each time, so a file added later shows at once. A memo and a comparison are given the files when they are written, and their marks watched only the chronology's events and the cameras. Each now remembers which path files its incident's cameras had (`paths_signature`, migration 0109), and one written before a camera's file was added, replaced or removed says so with the mark it already has: the memo's "The chronology has changed since this memo was written: a camera's path file was added, replaced or removed. Regenerate to write it on them.", the comparison's "a camera's path file changed since". A row written before this was kept is judged by the files' own dates, marked only when a file came after it. Nothing written is ever rewritten by itself. A chat answer already given stands as the record of what was asked then, and a recording's Summary is told nothing of the files, so neither is marked.

### Also in this release

`./transcribe folders`, `install`, `upgrade` and `basemap` asked whether each data folder existed without sudo, on a folder the operator cannot read, and so reported having made every folder on every run; the check asks with sudo now.

## 3. The Readings (the third release, v1.189.0)

### Words

**Reading**, as `CONTEXT.md` defines it: one moment a Path file records of its camera. The pages say "readings" and "the camera's file", never metadata, telemetry or flags.

### The Readings list

Each camera's row on the Map tab carries **readings**, which opens under the row the list of every moment its file records, in time order, each with its time of day on the case's clock (minutes into the recording for a camera off the clock), and for a spell (lights, siren, muted, stood still, no fix) its end. A press on a reading moves the clock there and lights the camera; where the reading is an event the map draws (and its kind is ticked), it selects it as a press on the pip would. The list is the chapter 1 events: camera on and off, the officer activating a body camera, the mic muted and back (a muted spell knows when the mic came back, from this release), the lights, the siren, the brakes, the crash sensor, a bookmark, a low battery, the top speed reached, each spell stood still, each stretch with no fix. An in-car unit's speed is drawn as a trace along its lane, scaled to its top speed.

### Offer to the chronology

On a reading in the list and on an event's card: **Offer to the chronology** makes a Proposed event on the recording (Phase 10 chapter 4) at the reading's moment, with the reading's words as its sentence, "Read from the camera's own file, not from the picture" as its why, the incident the camera is in where there is one, source `path` ("From the camera's file"), in the offerer's name. It waits on the Proposed events tab, and on the incident's Proposed events layer, for Accept or Dismiss as any proposal; accepted, it is a Note on the recording as any accepted proposal is, with the origin "from a proposed event (the camera's own file)". A reading is offered once: a second offer of the same words at the same moment is refused with the reason, and a dismissed one is not offered again. The button is withheld, with the reason, while the Proposed events tab is off in the office (the assistant's judgement off and no watch phrase listed), since the offer would have nowhere to land. `POST recording/<id>/path/offer` with JSON `t`, `until`, `words`; one audit row, "Reading offered to the chronology", with the reading's kind and never a position.

### Who was near here

**Who was near here** on the transport: pressed, the next press on the map asks the question of that place, marked with a ring. The answer is a card: every camera of the day that came within 50 m of the place, in the order they arrived, each with the spells it was there (a spell ends when a minute passes with no fix within reach), each a press to go there with the camera lit; or "No camera came within 50 m of here on this day." It is answered in the browser from the paths the page already holds: no request carries a position, and the server is not asked. Escape or Close clears it.

### What is not

No reading is offered by the app itself: Offer is the person's press, as Accept is. No position is in an offer, a proposal, a note or a row. The incident's own chronology gets the reading through the proposal's acceptance alone.

## 6. The Map tab refined: ticks, names first, tiles, the circle, and path files that wait (three releases, from v1.192.0)

### About

On 2026-11-04 the maintainer asked for the Map tab to be made more useful: a person should see only the cameras they choose (one, several or all); the trails should go off entirely; the list beside the map should be minimal, the officer's name first and matching the lanes under it, the rest behind a disclosure; when many cameras stand in one spot a line should lead from each to its name, and a press on the name should open a small video that moves with the camera, draggable and staying where dropped, four or more at once, with a vehicle's speed; path files uploaded before their videos, two hundred or more at a time, must not clog the chat or anything else; a circle a person can widen on the map should show which cameras passed inside it; and Add path files should move to the case's head, left of Add recordings. Added the same day: a note on one recording at the moment its video is on, and a note that applies to all the recordings at that moment; a pinned video's line follows the officer. Drawn in `docs/spec/mockups/phase-12-map-refine.html` (figures A to G, thirteen choices), which the maintainer agreed stands. Three releases: the list and the map (v1.192.0), the tiles and the notes (v1.193.0), the waiting files and the head's door (v1.194.0).

### Principles

1. **A tick is a view, not a truth.** What a person ticks changes what the page draws and nothing else: the chat, the memo, the comparison and the exports keep reading every camera with a Path. Ticks are remembered per person per case in the browser alone.
2. **The name is the person's.** The wearer as the file gives it comes first on the row, the lane and the tag; the unit is a fact behind the disclosure. A file with no name falls back to the unit.
3. **Nothing about the map's content leaves the browser** that did not before: the circle's centre, the leaders, a tile's place are the page's; the only server calls remain the video streams and the notes a person writes.
4. **A path file waiting for its video is kept, not read** (third release): no Path, no readings, no marker, no lane, nothing in any prompt. It becomes a Path only when its video arrives.

### 6.1 The list and the map (the first release, v1.192.0)

**Ticks.** Every camera of the day has a tick box on its row; the header's box ticks all or none (indeterminate when some are ticked) and "all" and "none" beside it do the same; a press on a row's name shows that camera alone, Shift adds it. Unticked cameras keep their row, dimmed, and lose their marker, trail, whole path, events and lane; **Fit shown** (Fit all renamed) frames the ticked ones; ‹ event and event › step the ticked cameras' events alone; the clock's span stays the day's. The unticked set is remembered in the browser under `map-hidden-<case>`, so a camera new to the case is shown by default. The incident page's pane has no list and draws every camera of its incident.

**Names first.** The row is the tick, the colour dot, the name the path file gives its wearer (a vehicle is its driver's name with "vehicle" after it; a file with no name shows the unit) and, for a vehicle, its speed while it moves; a ▸ opens the row to the rest: the unit, the kind, the surety pill with its why, the span on the clock, a vehicle's streams, **where it is now** (the street under the marker when a basemap is drawn, and the nearest other ticked camera with its distance, updated with the clock; never a coordinate), and the actions (Play here, Fly to, Readings, Open the recording, Replace file, Remove). One row opens at a time. The lane heads under say the same names in the same order, with the unit on hover. The "..." menu and the always-shown facts of chapter 1 are gone into the opened row.

**Trails off.** Show stays Markers only, Trails, Whole paths; **faint paths under** is a tick of its own, on by default, remembered per person: unticked, Markers only draws nothing but the markers and Trails nothing but the trails. Whole paths is unaffected.

**The leaders.** After every tick and every pan, the markers drawn are grouped by screen distance (within 30 px); a group of two or more gets a thin line from each marker to a tag with its colour and name, the tags placed round the knot's centre by each marker's bearing so the lines do not cross, clamped inside the pane. A lone marker keeps its small label. Pressing a tag is pressing the marker (Play here; a tile in the second release); a tag whose camera is followed, pressed or lit has a blue edge.

**The speed.** A vehicle moving over 3 in the file's unit carries its speed on a dark tag beside its marker, in its lane's head (as before) and at the end of its row.

**Within a circle.** Who was near here (chapter 3) grown a handle. Pressed, the next press on the map places a circle of 50 m there with a draggable centre and a draggable handle on its east edge; dragging the handle widens or narrows it (10 m to 5 km, the radius read beside the handle and on the transport), dragging the centre moves it. The list regroups to the cameras whose fixes fell inside at any time of the day, each with the span it was inside (first entry to last exit, a break of over a minute starting a new spell), in order of arrival, then "Never inside"; each lane marks its inside spells in a faint blue band; **Tick these** ticks only the cameras that passed inside. One circle at a time; "clear the circle", or Escape with nothing selected, removes it. It is answered in the browser from the fixes the page holds; nothing is kept, no row is written, no request carries a position. The chapter 3 card is replaced by the list's answer.

### 6.2 Tiles and the notes (the second release, v1.193.0)

A **Tile** is a small window on the map playing one camera's video at the clock's moment, muted, with the camera's colour, name and a vehicle's speed in its bar. It opens from a tag or a row ("Open a tile") beside its marker and rides with the marker, tethered by a dashed line; dragged by its bar, it pins where it was dropped and stays through pans, zooms and the clock's running, the tether redrawn every tick and every pan to wherever the marker is, running to the pane's edge in the marker's direction when it leaves the view ("out of view" in the bar). Up to six at once (the videos are the page's heaviest work), one with sound (the speaker in the bar, one tile at a time); "close all" on the transport beside the count; Pause pauses them all. Playing at 1× to 4× each tile plays its video at the clock's speed and is nudged back into step when it drifts over a second and a half; at 16× and 60×, or with the clock stopped, it shows the frame at the clock's moment, refreshed at most once a second, and says so; before the recording's start and after its end it says that instead. The video is the recording's playback copy, the same stream the Preview and the recording page play. Under 700 wide, one tile at a time. A press on the marker itself still opens the Preview (chapter 1); the tile is a tag's or a row's.

**Notes from the map.** The ✎ in a tile's bar writes a note on that recording at the moment its video is on, through the recording's note-at-a-moment route (`POST recording/<id>/note-at`) with `from: "map"`, which the server turns into `note_from` {kind map, words "from the map"} in its own words (any other origin the page claims is dropped); Note here and an event's Add a note now say the same. **Note on all shown** on the transport writes one note on every ticked camera that is running at the clock's moment, each at its own second (`POST case/<id>/map/note-all`, JSON `note` and `at` {recording: seconds}): ordinary notes (on the line being spoken, else at the moment), each with the usual "Note added" row and never the words, carrying one shared mark in `note_from` ({kind map-all, group, count, words "from the map, on 5 cameras"}). The Notes tab lists the group once, the first copy carrying the others ("on 5 cameras: A, B, C, D, E"); each camera's own page, the Preview and the exports show their own copy; a chronology marks each camera's copy on that camera's lane, a lane being one camera's. Editing a copy edits that copy: the group is a listing, not a lock, so a note corrected on one camera says so there and the others keep their words until corrected too (a build choice; asking whether to change all was drawn and is left for the maintainer's word if wanted).

### 6.3 Path files that wait, and the head's door (the third release, v1.194.0)

**Add path files** moves to the case's head, left of Add recordings, on every tab (while Maps is on and the person may add to the case), and leaves the Map tab's lead; the per-row Add a path file, Replace file and Remove stay on the Map tab. The head's door is its own small script (`path-files.js`): a folder's worth of files is posted to the same `case/<id>/paths/add` in batches of twenty (two hundred files in one request would be too large), the answers merged into one layer: **Added to their videos**, **Waiting for their video**, **Flagged**, **Already has one**, **Refused**, with the flagged and already-taken files to settle (Add anyway, Replace) as before, and "On the Map tab" when the layer was opened elsewhere. The Map tab, when it is open, reads its paths again when the layer closes.

A path file whose name matches no video in the case is no longer a leftover to settle with a chooser: it is kept on the case as a **waiting file** (`WaitingPathFile`, migration 0105: the case, the file's name and stem, its size, its kind and cue count from the same one look the take-in gives every file, who added it and when; its bytes under the case's folder in `waiting/<id>.vtt`), with no Path. It is on no map, in no lane, in no chat block, no memo, no comparison, no Speakers page offer, and has no readings: everything that reads paths reads `CameraPath`, which a waiting file is not. The Map tab's list carries the fold **Waiting for their video: N path files** (kept on the case, not on the map) with Find by file name, Remove on each, and Remove all waiting behind a confirm; the Details tab's On the map line counts them. A file of a name already waiting is not kept twice. Its audit row is "Path file kept waiting" (the case, the kind, the cue count; never the wearer, the unit or a position); removing writes "Waiting path file removed" or "Waiting path files removed" with the count.

**Pairing.** When a recording lands in the case, the app looks for a waiting file of its name by the same stem rule the take-in uses and pairs it: the file becomes the recording's Path through the same `add()` with the usual "Path file added" row, which says `paired_from_waiting`. Two moments land a recording: the pipeline making it Ready (an upload into the case, where the length is then known) and a move into the case; renaming a recording changes its title and not the file name the stem reads, so a rename pairs nothing (the drawing said it would; the build found no name to read). The unit and length checks still apply at pairing: a file that disagrees with its video stays waiting, the fold saying "Matches BWC3-1 by name, but: ..." with **Add anyway**, which pairs it as the take-in's Add anyway does; a video that already has a path keeps it. A waiting file whose video never comes stays until someone removes it or the case is deleted (it goes with the case's folder). Pairing in the pipeline is a courtesy around the recording's own work: a failure there is logged and never fails the recording.

This amends ADR 0029: a Path is still made only on a Recording; the file may wait on the Case. The pairing's actor is the person who landed the recording (a move), or, from the pipeline, the person who added the waiting file.

### 6.4 Names that move like the video, and videos that resize (the fourth release, v1.195.0)

Asked on 2026-11-04 after v1.194.0 and drawn in `docs/spec/mockups/phase-12-map-tags.html` (figures A to C, eight choices), agreed the same day.

**Every marker carries its name.** Not only a knot: each marker drawn on the map has a tag with its colour and the officer's name, led out on a thin line, riding beside the marker where the app places it. A press on the tag opens the camera's tile (on the incident page's pane it brings the camera to the front of the wall, as the marker's press does); a drag moves it.

**Names move like the video.** A tag dragged pins where it is dropped (a blue edge and a pin mark), stays through pans, zooms and the clock's running, its line redrawn every tick to wherever the marker is, to the pane's edge when the marker leaves the view ("out of view" after the name); a press on the pin mark lets it ride again. Opening the tile from a tag puts the tile in the tag's place, pinned if the tag was; closing the tile puts the tag back where the tile was, pinned as the tile was. The tile's bar has the pin as a button for the same purpose. Pinned places last while the tab is open and go with it (choice 3).

**The video carries the name.** A camera whose tile is open has no tag: the tile's bar is its name, and the one line runs from the marker to the tile.

**Nothing overlaps.** Names and tiles are rectangles that may not touch (a 4 px gap) nor cover a marker (14 px round it). Each tick, the pinned ones and the one being dragged are walls; the riding ones, tiles first, each take the nearest free place to their marker, searched outward in rings, sideways first, so a crowd spreads into columns beside its knot (choice 8 answered as rings sideways: the effect the columns were drawn for, without a second rule). **Resizing.** Every tile has a grip at its lower right corner: dragging it sets the tile's width from 120 px to half the pane, the picture keeping a 16:9 proportion; a resized tile pins where it stands; the width settled on becomes the width the next tiles open at, remembered per person (`map-tile-w`); a double press on the grip puts the tile back to 168 px.

**Save a picture** draws the names and the lines where the person left them, each tile as a frame with its name in the bar and the frame its video is on. Nothing new is kept on the server; no row is written.

### 6.11 The jump rules (the eleventh release, v1.211.0)

The maintainer's screenshot of 2026-11-05 from the office's own server: one camera's path with its real route around the town and a fan of long straight lines all meeting at one far-off point. The file reports a fixed far position every so often between its real fixes (a stale or "home" fix: the dock, the vehicle, or the last position before the camera lost its lock), and `parse` kept every fix and broke a path only where ten seconds passed with no fix, never at an impossible distance. Three rules now, in `camera_paths.clean_fixes`, run at the end of `parse` on the fixes as read:

- **The repeated far point.** A coordinate that recurs `HOME_FIX_TIMES` (3) times or more, and is far from the fix before or after it on two thirds of those occurrences, is left out everywhere, each occurrence a mark `[t, "dropped", metres]`.
- **The spike.** A fix further from both its neighbours than `JUMP_METRES_PER_SECOND` (70 m/s, about 150 mph) allows, while its neighbours are within that of each other, is left out with the same mark; the pass repeats until no spike is left.
- **The jump kept.** A step still faster than the ceiling between two kept fixes is marked `[t, "jump", metres]` at the later fix; `map.js` breaks the path's line there (`prepare`), so no stroke crosses the city, and the fixes on both sides stay.

Nothing is invented: a reading the file carries is left out, and the readings say so. `events_of` gives each mark as a reading ("A fix 9.2 km away left out", "Jumped 9.2 km: the line is not drawn"), the camera's opened row and `words(path)` count them ("14 fixes left out as jumps"), `map.json` carries `dropped`, and the chat's readings block says "N fixes left out as jumps the camera could not have made". The bounds, the trail, the stood-still spells and the together readings follow the kept fixes, so the map fits the real route again. No offer to the chronology from a jump reading. `READ_VERSION` is 2 and the minute task now calls `camera_paths.read_again_the_old` beside the documents' re-read, so every path file already on the cases is read again with the rules; until this release that call was missing.

### Add a document

- **One lighter page** (`document-add.html`): the eyebrow (the case, Documents), the title Add a document, the PDF (a drop zone that is the file field), the title, **About** (Nothing in particular, as shipped; an incident of the case; a camera of the case, each a plain choice with its picker), **Compare when it is read** (Not yet, as shipped; Against the case; Against the incident it is about, offered only with an incident chosen), Add and Cancel, and the what-fits line in small type (PDFs only, the page ceiling, the case's cap with the count so far, OCR, nothing leaves the building). `add-document?incident=<id>` and `?recording=<id>` still arrive from the incident's and the recording's Details with the about pre-chosen.

Nothing starts a nine-minute reading by surprise: the choice is off unless pressed.

## 12. What the case holds decides its tabs (v1.214.0)

### About

The maintainer's ask of 2026-11-06: an audio-only case should carry only Recordings, Search, Notes, Speakers, Clips and Details, with no map; Add path files should be offered only once a video is in the case; the Map tab and everything that goes with it should appear only once the case has at least one valid path file, so a valid path file is a feature unlock for the case. The drawing `docs/spec/mockups/phase-12-case-unlocks.html` (the three states as case bars, every piece of the map feature with its rule, the words on the pages, six choices) stands; on the two tabs the build argued for keeping on an audio-only case, Proposed events and Documents, the maintainer's word is to hide both.

### Principles

- **What the case holds decides, nothing is set.** Three states, read from the recordings and the path files: **audio only** (no recording of the case has a picture, by the probe the Incidents tab already reads), **video** (at least one has), and **unlocked** (at least one recording of the case has a path file that was read: a Path row). A case moves between them by itself as recordings and path files come and go; nothing is pressed and nothing is kept.
- **The Panel's switches stay the masters.** Maps off, Documents off, Incidents off, Clips off and the assistant off hide their tabs everywhere as before; the case's state only narrows further.
- **One helper.** `cases.holds(case)` answers `has_video`, `has_path` and `waiting` (path files waiting for their video), read once per page and handed to the case bar, the case page, the Map page, the take-in and the pills; nobody asks twice.
- **Nothing is a dead page.** A hidden tab's address answers with the Recordings tab and one notice; an old On the map link never breaks.

### The states

- **Audio only.** Six tabs: Recordings, Search, Notes, Clips (while on), Speakers, Details. Proposed events, Documents, Incidents and Map are hidden whatever the office's switches say. No Add path files in the head. The incident pills (not synced, events to check, proposed events waiting, memos) are not drawn on Home or the case page, since the tabs they lead to are absent. The Details tab's On the map line reads "none. This case holds sound recordings only; the Incidents and Map tabs appear once a video is in it."
- **Video, no path file.** Every tab but Map, as the switches allow. **Add path files** in the head. No Map tab, no "cameras on the map" pill, no small map on the Incidents desk (its right column gives the room to Your incident and Built on this day) and no Tick the near or near marks there (Tick everyone running now stays), no On the map anywhere, no Map pane on an incident. The Details line reads "none yet", says what a path file is and that the Map tab appears with the first, and counts the path files waiting for their video; the Add path files button's title says the same.
- **Unlocked.** The Map tab with its count, the pill, the desk's small map with its near tools, an incident's Map pane where a camera of it has a path, Save a picture, Within a circle, the readings told to Gideon and the memo: the whole feature set, as today. Most of it was already gated per camera (On the map, the readings, the pane); the rule adds the case level.

### Where the rule reaches

- `case_bar.bar` draws Proposed events, Documents and Incidents only with a video and Map only when unlocked (and the switches on); the case page's tab list follows, and a tab asked for by address that is hidden falls to Recordings with the notice ("This case holds sound recordings only, so it has no Incidents tab" and the like).
- The Map page answers only when unlocked; otherwise it sends to the Recordings tab with "No camera in this case has a path file yet, so there is no map to show." The case page's `?tab=map` goes through it as before.
- The take-in of path files (`case-paths-add`) refuses a case with no video: "Add a video to the case first: a path file belongs beside one."
- The Incidents desk's small map is mounted only when unlocked; `chronology.js` draws Tick the near only while the map host is on the page.
- `dashboard.pills` draws the incident pills only for a case with a video (the grouped query now counts the videos too); the "cameras on the map" pill was already hidden at zero.
- A waiting path file (chapter 6) unlocks nothing; it is counted on the Details tab and the button's title until its video lands, when the Map appears by itself.

### What is not

No per-case setting, no store, no migration, no audit row. The incident page's Map pane, the On the map links and the readings keep their per-camera rules. The Panel's Status page, the basemap and the Maps setting are the office's, unchanged.
